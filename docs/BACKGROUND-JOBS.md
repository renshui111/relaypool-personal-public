# 后台任务与超时隔离

## 解决的问题

后台任务按顺序遍历账号。过去目录刷新和登录态续期直接使用整个调度循环的上下文；单个平台长时间不返回时，后面的账号也一直等候。2026-11-09 起，这两类任务为每个账号设置独立期限，超时后继续本轮后续账号。

本轮不改变数据库结构、账号配置和任务时间。目录超时不禁用账号、不清空已有目录；登录态续期失败不保存失败结果。原有凭证保存仍使用持久层的并发更新保护。

后续补齐了适配器未提供原始凭证快照时的写回保护：后台保活和签到前续期现在都由调度器保存快照，禁止直接覆盖新登录或重新插入已删除凭证。详见[登录态续期保护](CREDENTIAL-REFRESH.md)。

## 任务何时运行

| 任务 | 默认时机 | 单账号期限 | 失败后的行为 |
| --- | --- | --- | --- |
| 模型目录刷新 | 启动约 5 秒后第一次；每轮完成后等待 30 分钟 | 30 秒 | 保留原目录，继续后续账号；等待下一轮或手动查询 |
| 登录态续期 | 本地时间 22 点所在小时内 | 60 秒 | 保留原凭证，继续后续账号；记录失败日志 |
| 签到／奖励领取 | 本地时间 9 点、21 点所在小时内 | 60 秒，已有行为 | 按平台能力、账号开关及领取周期处理；同号进行中的请求不重复启动 |
| 过期冷却清理 | 每 5 分钟 | 不访问上游 | 清除到期冷却记录 |
| 请求日志清理 | 启动一次，此后每小时 | 每轮 20 秒 | 默认保留 7 天，保留天数为 0 时不运行 |

定时小时按运行环境时区，默认 Compose 为 `Asia/Shanghai`。每分钟检查一次小时任务，因此不是保证整点执行；在进程存活期间，同一任务同一小时只触发一次。重启会重置小时触发记录，签到还受持久化领取周期记录约束。

仅启用的账号参与目录刷新与续期。已知访问令牌有效期还超过 6 小时时，续期跳过该账号；有效期未知或接近到期才尝试。自动签到还要求账号开启自动领取，且平台和地区支持；这不意味着所有平台都有每日积分。

## 期限和取消的区别

30／60 秒是单次后台任务期限，不是整个账号池一轮的期限，也不是聊天回复期限。目前这两个期限写在调度器内部，没有独立配置项。任务顺序执行，多个慢账号仍会累计等待；此轮没有引入并发访问上游。

上游适配器自身的更短超时仍生效。停止服务或父上下文提前取消时，当前请求跟随取消，不再启动后续账号。适配器须遵守传入的上下文；对忽略取消、永不返回的自定义适配器，调度器不能强制结束其执行。没有额外创建脱离调度器生命周期的后台协程。

配置刷新间隔、调度小时和时区见[配置参考](CONFIGURATION.md)。流式聊天的空闲超时见[流式连接管理](STREAM-LIFECYCLE.md)，与本页的后台期限不同。

## 启停与重启

2026-11-09 后续更新修复同一调度器实例的启停竞态。原实现先将“运行中”设为否，再等待旧任务退出，期间另一调用者可以启动新任务；启动时也先释放状态锁，再登记后台任务数量。现在启停过程使用独立的互斥锁，贯穿任务登记、取消和退出等待。

- 已运行时重复启动不会创建第二套任务；已停止时重复停止直接返回。
- 停止发出取消信号，并等待本实例登记的目录刷新、冷却清理、日志清理及小时任务全部退出。
- 停止尚在等待旧任务清理时，新启动等待；旧任务退出后才创建下一轮。
- 已取消的启动上下文不创建任务，也不妨碍后续有效启动。
- 同一实例重启保留小时去重记录；整个进程重建才重置内存中的小时记录。签到的持久化领取周期记录仍保留。

这项保护作用于一个进程内的调度器，并不增加管理台重启按钮，也不协调多个容器。适配器和任务回调仍需响应取消；忽略取消的回调仍可能拖住停止。开发时在启动前安装清理回调，回调内部不要调用本调度器的 `Start` 或 `Stop`，避免自等待。

## 排查方法

1. 先检查账号是否启用、凭证是否完整；续期还需核对令牌有效期，跳过新令牌属于正常行为。
2. 执行 `docker compose logs --since 30m --tail 200 relaypool`，查找 `scheduler: catalog`、`scheduler: keepalive` 和 `deadline exceeded`。退出时的取消与运行中的上游超时需结合发生时间区分。
3. 后台失败不会主动清空旧目录，所以“列表里有模型”不等于刚刚刷新成功。管理台发起一次目录查询或短消息验证当前可用性。
4. 反复超时时检查出站代理、平台状态和登录态；修复后重新查询，或等待下一轮。不要通过删除数据卷重试。

向公开仓库反馈时仅提供脱敏的错误和版本；账号标识、授权回调、令牌和数据库不附在问题里。备份及回滚步骤见[维护说明](OPERATIONS.md)。

## 验证方法

新增受控测试使用虚拟时间：首个账号一直等到取消，后续账号立即成功。分别验证目录 30 秒、续期 60 秒后继续；原目录保留、超时后迟到的目录不写回；只有成功账号进入凭证保存；父级 1 秒期限或主动取消优先且不触发后续账号。该测试不访问外部平台。

自动检查：`go test ./...`、`go vet ./...` 和 `go test -race ./internal/scheduler` 通过。

额外的 API 竞态检查首次出现一次异常报告，堆栈位于已有的 `armor.BundledResearchFiles` JSON 解析路径。本轮未修改该路径；单独重跑相关用例通过，随后 `go test -race ./internal/api -count=2` 连续两轮通过。目前未能复现或确认首次报告的根因，不能据复测宣称该异常已修复。
